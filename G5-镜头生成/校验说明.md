# G5提示词校验

正式提示词采用“官方模板匹配、程序检查、逐镜内容复核、提交前核对”流程。程序失败或必要复核缺失时停止正式交付和提交；没有跳过检查或自由格式放行选项。

## 准备任务记录

执行者为每个独立请求维护一份[JSON任务记录](模板/校验任务.json)，与纯文本提示词一起保存于项目的内部校验目录。复制给视频模型的只有提示词正文；JSON字段服务于工作记录，不是模型输入格式。项目的人类阅读稿使用四类Markdown模板。

字段约定：

- `task_id`、`profile`、`mode`、`entry`：准确任务与分支；分支配置见[模型模板登记](模型模板/分支配置.json)。
- `plan_file`、`group_id`：本次生成分段方案的相对路径及当前段号；方案按[分段模板](模板/生成分段方案.json)记录本次分镜范围、来源SHA256、每段镜号与时长及合并/单镜理由、每对相邻镜头的合并/拆分判断与理由。多个任务可引用同一方案。用户只指定单镜时，范围只包含该镜并记录原因。
- `fixed_context`：固定描述文件的`path`、`sha256`、`project_id`、`version`，本次实际涉及的场景状态`scene_ids`、无需场景时的具体`scene_omission_reason`，以及实际内容核对`reviewed`和`review_evidence`。项目文件结构见[固定描述规范](../固定描述规范.md)；每个已确认场景含`id`、`applies_to`、`confirmed`、`confirmation_evidence`和按分支保存的`texts`。程序检查确认、版本、分支及画风/适用场景原文是否包含，内容复核负责场景清单完整性和语义冲突。该文件实际内容进入输入指纹。
- `prompt_file`：相对任务JSON的完整提示词文件，不含外层代码围栏和解释。
- `draft_review`：初稿单独保存；登记初稿`path`、`sha256`、是否已完成逐镜检查`completed`、`reviewer`、`reviewed_at`、按顺序覆盖的`reviewed_shots`及复检`summary`。`issues`逐项写镜号`shot`、具体`finding`、本镜分镜原文`source_quote`、初稿相关原文`draft_quote`（漏写时可空）、第二版对应原文`revision_quote`及是否已解决`resolved`；确无问题时用空数组。`prompt_file`指向单独保存的完整第二版或之后的完整修订版，初稿与当前版本不可共用同一路径。初稿、分镜、资产或当前稿变化后重新检查并绑定。字段记录和程序匹配不能证明复检真实发生或清单完整。
- `draft_review.review_method`在实际完成独立子代理复检后写`independent_subagent`，`review_evidence`记录可追溯的子代理任务与结果；未完成时保留空值。程序仅检查记录存在，不能验证代理确实独立或实际完成审读。
- 如初稿问题涉及应转交后期的分镜画面文字，`issues`用`resolution: deferred_post`和`post_note`记后期安排，保留分镜依据；不得为了填`revision_quote`而在第二版添加画面文字指令。
- `source_files`：本次实际分镜及有效要求文件，登记相对路径和SHA256。
- 分段方案的`source_sha256`填写本次分镜来源摘要，每个任务的`source_files`须包含这些来源，其他有效要求文件可按段补充。`scope_shots`按本次范围的原镜号顺序完整列出；每个镜号恰好属于一个生成段。`boundaries`对相邻镜头依次填写`left`、`right`、`decision`（`merge`或`split`）与具体`reason`；多镜合并或拆分须与实际生成段一致。
- `references`：实际输入素材的路径、SHA256、模型标签、职责、选用状态与依据。纯文生为`[]`；尚未选用素材不能自动视为已选。
- `reference_requirements`：先对照当前用户要求及资产清单，登记完整需求及依据。`reviewed`为是否已人工核对需求清单，`basis`记核对依据；`items`逐项写`name`、`role`、`basis`、适用镜号数组`shots`、实际绑定`label`、`verified`和`binding_evidence`。真实文件、选用状态及摘要仍在`references`登记；未找到或未核实的需求保留并写`verified: false`，不得从清单消失。确实无需参考时核实后填空数组。程序不能发现清单本身遗漏的要求，也不能试听或判断音色相似。
- `duration_assessment`：`source_seconds`为本段原分镜估计时长合计，`basis`写镜号及依据；`status`为`pending`、`estimated`或`measured`。压缩段未实测时照实登记，交付提示词明确标出容量待验证；生成前再完成试读及动作反应共用时间轴核验，填入`measured_seconds`、`method`及可追溯的`evidence`。程序只能检查记录完整性和数值，无法验证实测真实性或表演自然程度。
- `shots`：按请求顺序列实际镜号，`dialogue`逐句登记`text`、`speaker`与`voice`；无台词为`[]`。
- `parameters`：实际入口的参数，至少登记`duration`及本次画幅、声音等条件。程序检查中可确定的格式条件，具体供应商参数须按对应官方API或界面核实。
- `sound_policy`：本次声音目标。`sound`表示保留环境、动作、人声或音乐等实际需要的声音，只有明确要求全程静音时填写`silent`。没有配乐不等于全程静音；`parameters.audio`记录实际入口的音轨开关，不能代替本字段。H3声景写`N/A`时须对应`silent`。
- `official_reads`：本次实际读取的官方规范URL；参考技能或第三方配置不代替读取。
- `runtime`：实际入口、模式、参数及引用能力的核实状态、时间和证据；未核实写`false`。
- `authorization`：是否获准生成及具体范围。提示词准备授权不变成视频生成授权。
- `review`：实际逐镜复核结果、证据和当前输入指纹。

H3登记涵盖五种模式。即梦2.0和2.5分别登记纯文生及一般参考模式，采用官方指南的镜序写法；专用编辑、延长、关键帧、flash或其他入口先读取相应官方模板并建立匹配登记，不用一般模式替代。规范更新先核对来源，再更新登记和程序；不为通过现有任务降低规则。

2.5镜头内采用显式时间区间时，起止为非负整数秒，满足`0 <= 起点 < 终点 <= 请求总时长`，区间在镜头开头或正文中部均需核对。对白和画面文字按规定符号或引号保留，其字面数值不当成时间控制。参考素材的源区间放在镜头前的素材指代部分并注明来源，区别于成片时间。无时间轴的镜序写法照常适用，局部时间安排不强制填满全部时长；跨镜顺序、声音延续与叙事衔接仍按分镜实际复核。

## 逐镜内容检查

`review.coverage`以实际镜号为键，每镜分别填写`size`、`angle_composition`、`camera`、`subject`、`action`、`environment_light`、`style_constraints`。每项记录`status`、分镜原文`source_quote`和提示词原文`prompt_quote`；镜内证据须位于对应镜头。确属本任务共享设定时标`scope: shared`，并人工判断每镜确实继承该设定。

某项经人工确认确实不适用于该镜时，可填`status: not_applicable`并在`reason`写依据，不为凑齐表格虚构要求。程序不能替代不适用判断。

`review.source_bindings`以镜号为键，登记`path`（须属于`source_files`）和该镜完整的Markdown标题行`heading`；程序定位唯一标题及至下一个标题之间的正文。其他分镜排版先转换为忠实的逐镜Markdown并保留原文与版本映射，不能猜测分界。共享依据须写`scope_reason`。`review.detail_checks`以镜号为键，写逐条数组，每项含`item`、`status`、`source_quote`、`prompt_quote`；确实适用的共享项可填`scope: shared`及`scope_reason`。先逐条提取实际要求，再写稿并补入对应原文；单项必须拆分光源与受光、机位起止、人物关系、动作状态、台词重音和跨镜承接中实际存在且独立影响画面的细节，不用一个泛化引用代表整类。音色和资产的来源、职责及版本同时在需求和实际绑定中核对。程序验证引文位置，不能判断细节是否全部列出、是否同义或准确。

分镜要求的画面文字转交后期时，在对应细节中记`status: deferred_post`、该镜`source_quote`及`post_note`（文字内容与后期交接位置）；不将其当作缺漏补回视频提示词。程序核对来源与记录是否填写，不证明后期交接文件已实际完成。

`review.judgments`逐项记录`dialogue_speakers`、`states`、`sound`、`continuity`、`clarity`、`current_basis`和`music_subtitles`，每项填写`status`与具体`evidence`。分别检查说话人及声源、动作起止、声音落点、镜间接法、单义简洁表达、当前有效依据，以及无背景音乐、画面无任何文字且不误删对白和音效；原分镜要求的文字交给后期。通过项写`pass`，其余保留`pending`或`fail`。不能只把所有格子填为通过而不实际对照。

H3的`non_diegetic_music`固定为`N/A`，画面描述中写一次`No on-screen text. No subtitles. No background music.`；即梦2.0与2.5的自然语言中写一次`画面无任何文字，无背景音乐。`。程序核对这些明确写法，人工仍须检查其他段落是否有文字或音乐指令、需要的声音是否保留，以及实际生成结果；提示词约束不保证模型一定遵循。

台词原文清单必须先对照分镜，确保清单本身没有漏句。程序将清单与提示词逐字对比，但不能发现清单和提示词一起漏掉的内容，也不能代替说话人、动作因果与审美判断。跨镜对白按官方标签承接后，对分片文字及整句原文一并复核。

## 绑定与运行

使用Python3标准库，无需安装依赖。先完成逐镜内容检查，计算本次输入指纹，将结果写入`review.fingerprint`；指纹用于将实际检查绑定到这份稿件，不是内容检查本身。

```python
import importlib.util
from pathlib import Path
script = Path("技能目录/G5-镜头生成/scripts/validate_task.py")
spec = importlib.util.spec_from_file_location("g5_check", script)
module = importlib.util.module_from_spec(spec)
spec.loader.exec_module(module)
print(module.fingerprint("项目内部校验目录/任务.json"))
```

正式检查：

```sh
python3 "技能目录/G5-镜头生成/scripts/validate_task.py" "项目内部校验目录/任务.json" --report "项目内部校验目录/校验结果.json"
```

退出码`0`表示程序所能检查的模板、绑定及已登记复核齐备；人工仍须确认逐项清单完整和语义准确。`1`表示格式、引用或证据等检查失败；`2`表示缺少必要复核或执行条件。`format_result`汇总模板结构及内容复核之前的程序检查，包含分段、引用和摘要检查，并非单独的语法结果；`content_review`表示所登记内容复核的状态，不是语义自动验收。交付提示词须报告`duration_risk`等未验证事项；`generation_ready`还要求容量核实及实际生成授权。程序自身不调用模型，不消费额度。

程序核对分段方案的范围、来源摘要、逐对判断、镜号顺序、当前段和时长，及模板登记、模型结构、引用与文件摘要、镜序与切点、台词文字、七要素证据及复核记录绑定。程序不能判定分组理由是否合理或是否遗漏实际分镜，须实际逐镜审核并核对所请求范围；不能判定的语义、矛盾、冗余和画面效果也由实际复核承担。分段方案及其他输入改动后旧指纹失效，重新检查后再使用；单独补录生成授权不改变提示词内容检查指纹，提交前仍须核对授权。

提交前核对实际发送的正文、引用顺序与参数是否和通过检查的输入一致，保存最终输入与报告。使用通用外部工具时同样执行此步骤；本地校验不会控制未接入本流程的账户或软件。
